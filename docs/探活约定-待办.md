# 探活约定：待办备忘

> 状态：**本轮先不改代码**。来自「悠度假」跑流问题梳理；探活涉及模板分型、状态码白名单、业务码/HTML、假绿链，范围大于眼前补丁，单独记档，后续立项再动。

## 1. 为啥先搁置

- 不只是「白名单再加个 403」：要分清探活到底判什么、和登录流怎么接、预制模板/Skill/MCP 示例一起改。
- 和「失败仍写 extracts → 脏凭证」叠在一起才会假绿；**脏凭证门禁**可先修，探活模板后动也能减一半风险。
- 对方后端形态不一（401 / 403 / 总是 200+业务码 / 200+HTML 登录页），一刀切模板容易误伤。

## 2. 悠度假实证（库内）

项目：`悠度假`（`test_project_id=2103043828113203200`）

- 管理端探活：`POST /system/main/toDoList`
- 未登录时：HTTP **200** + **HTML 登录页**（文案含「未登录或登录超时」），**不是 401**
- 现图：`statusCheck whitelist [200,401]` + `successCheck=off` + `Condition(http.status=200)`
- 假绿 run 例：`test_flow_run_id=2103317463948255232` —— 凭证 exists → 探活 200 HTML → 「探活是否成功」走 IF → **整流 passed、未走登录**

假绿链（与 extracts 问题叠加）：

```text
登录业务失败 → 仍抽 Set-Cookie 写 asset
  → Condition 凭证 exists=真
  → 探活 HTTP 200（实为登录页）
  → Condition status=200 → 整流假绿
```

## 3. 现状模板（质衡）

统一骨架（文档 / Skill / 预制流）：

1. `Condition(凭证 exists)`
2. 探活 HTTP：`statusCheck: { mode: whitelist, values: [200, 401] }` + `successCheck.mode=off`
3. `Condition(http.status=200)` → IF 无出边（视为已登录）；ELSE → 登录

相关位置：

- `PrefabricatedTemplateExtrasSupport.builtinLoginFlowJson`
- 前端 `buildLoginGraphJson`（若仍有同构）
- `docs/mcp.md`、`McpCursorSkillService` 示例、`flow-design-tools.json` 中 statusCheck 描述

## 4. 后续建议：探活三型（未落地）

不要再叫死「401 型」。更准确：

| 类型 | 失效长什么样 | 建议骨架 |
|------|----------------|----------|
| **HTTP 鉴权失效状态码型** | 401；实务常还有 **403** | 白名单建议 `[200, 401, 403]`（活着 + 去登录）；IF 仍 `status eq 200`；**不要**把 5xx/404 塞进「去登录」 |
| **业务码型** | HTTP 几乎总是 200，看 `body.code` | 探活开 `successCheck`（跟 Profile `responseConvention`）；IF 看业务成功或步骤 biz 成败 |
| **HTML / 非 JSON 型** | 未登录回登录页 HTML（悠度假管理端） | 读不到业务码 / body 非 JSON → **应判未通过**，不能只看 200 |

说明：

- 只加 403 **治不好悠度假**（它是 200 HTML）。
- 5xx 应让探活步骤失败（故障），不要当成「去登录」。

## 5. 以后动手时建议改哪些

- 文档 / Skill / MCP 示例：写清三型，勿对业务码/HTML 型单独依赖 `Condition(http.status=200)`
- 预制登录流：按 Profile 约定选骨架（或造流时让人选探活类型）
- 工具 `statusCheck` description：旁注探活白名单语义（活着 vs 去登录 vs 故障）
- （可选）探活节点能力：非 JSON / 业务码解析失败时的明确失败语义，避免「200 即活」

**本轮不改上述项。**

## 6. 和本轮其它修复的关系

| 项 | 本轮 | 对假绿的影响 |
|----|------|----------------|
| 失败不写 asset extracts | 做 | 打断「脏 Cookie → exists 真」 |
| TF_BIZ_CODE 路径/摘要 | 做 | 登录失败说人话，与探活模板无关 |
| 探活模板 / 分型 / 403 白名单 | **不做**，见本文 | 未登录 200 HTML 仍可能假绿，需后续立项 |

## 7. 待决策（立项时再定）

1. 状态码型默认白名单是否从 `[200,401]` 升级为 `[200,401,403]`（兼容性、是否误把真 403 权限不足当成去登录）。
2. 业务码型 IF 条件用「探活步骤 passed」还是显式 `http.body.<codePath>`。
3. HTML 型：靠 bizCheck 解析失败，还是单独「响应必须是 JSON」门禁。
4. 存量项目（如悠度假）是否提供迁移/一键改探活节点，还是只改新生成模板。
