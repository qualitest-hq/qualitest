# 测试流写锁去留：决策稿

> 状态：待决定。起因是「一键排版会占写锁，挡住 MCP」。本文对比两条路线，给出推荐与改动范围。

## 1. 现状

### 1.1 写锁怎么工作

- 服务端 [`FlowEditLeaseService`](../qualitest-system/src/main/java/com/qualitest/flow/sync/FlowEditLeaseService.java)：Redis `SET NX`，键 `qualitest:flow:edit-lease:{testFlowId}`，TTL 45 秒。
- Web 端 [`useFlowEditLease.ts`](../qualitest-ui/apps/web/src/views/project/testFlow/composables/useFlowEditLease.ts)：画布 `dirty` 即抢锁，每 20 秒心跳；保存变干净、离开画布、切流时释放。token 存 sessionStorage，刷新后先续约。
- 保存 [`TestFlowServiceImpl.updateTestFlow`](../qualitest-system/src/main/java/com/qualitest/project/service/impl/TestFlowServiceImpl.java)：写 `graph_json` 前 `beginWrite`。请求头带有效 `X-Flow-Edit-Lease` 则续期沿用，否则短抢短释。
- MCP / Web 全自动落盘 [`FlowDesignAutopilotCommitSupport`](../qualitest-system/src/main/java/com/qualitest/ai/tools/flow/FlowDesignAutopilotCommitSupport.java)：同样走 `updateTestFlow`，撞锁返回 `lockHeldBy`。

### 1.2 一键排版为什么会挡 MCP

[`useFlowTidyLayout.ts`](../qualitest-ui/apps/web/src/views/project/testFlow/composables/useFlowTidyLayout.ts) 写完坐标后 `store.markDirty()`，于是 Web 开始长占锁，MCP `submit_*` 落盘撞 `lockHeldBy`。拖拽节点同理（[`nodeChangeAffectsPersist`](../qualitest-ui/apps/web/src/views/project/testFlow/utils/nodeChangeAffectsPersist.ts) 把 `position` 视为持久化变更）。

AI / MCP 本身不改已有节点坐标：[`FlowDesignPatchNormalizer`](../qualitest-system/src/main/java/com/qualitest/ai/scenario/flow/FlowDesignPatchNormalizer.java) 丢弃入参坐标，update 保留画布原位置，只给新增节点自动排版。

### 1.3 锁真正防的是什么

保存是**整图覆盖**，且**没有版本校验**。锁防的是「丢失更新」：

1. 用户改了画布（脏），未保存；
2. MCP 写入新节点；Web 因为脏，只亮「放弃本地并拉取」条幅，不自动合入；
3. 用户忽略条幅点保存，本地旧拓扑覆盖 MCP 节点，**静默丢失**。

因此「只在保存时加锁」无效：保存时本来就会短抢锁，但挡不住基于旧图的覆盖。

### 1.4 现有锁的问题

- 挡人过多：拖一下、排一下版，MCP 就被挡。
- 机制重：心跳、TTL、sessionStorage token、刷新续约、关页后锁残留最长 45 秒。
- 本就是尽力而为：Web 抢锁失败仍允许本地编辑（`useFlowEditLease` 中「抢锁失败仍可本地改图」）。
- Web 全自动基准过旧：设计请求带的是前端画布（`request.getGraphJson()`），一轮对话中累积单元，跑流前或回合结束才落盘。期间 MCP 写入会被这次落盘覆盖，锁挡不住。
- 疑似自挡（读代码推断，未实测）：Web 设计请求不带本标签 lease token，本页脏时全自动落盘可能撞上自己标签持有的锁。

## 2. 路线对比

### 路线 A（推荐）：去掉写锁，改为乐观版本校验

给流加版本号，所有写 `graph_json` 的入口条件更新，冲突时按写入方分别处理。

| 写入方 | 基准图来源 | 冲突时处理 | 是否会被拦 |
|:--|:--|:--|:--|
| MCP `submit_*` | 每次从库加载（`McpToolInvokeService.ensureWriteEnvelope`） | 服务端重读、重放本单元、重校验，自动重试若干次 | 基本不会 |
| Web AI 半自动 | 不写库，Staging 只改本地画布 | 同人手保存 | 不涉及 |
| Web AI 全自动 | 回合开始时的前端画布 | 拉最新图，重放本轮 capture 中已接受单元，重校验后写；重放失败才报错 | 常见情况不会 |
| 人手保存（含排版、拖拽） | 加载时的图 | 仅坐标变：自动基于最新图套回本地坐标再存；改了内容：弹冲突 | 仅内容冲突时需人决定 |

**优点**

- 一键排版、拖拽、改内容草稿都不再挡 MCP / Web AI。
- 删除整套租约机制（心跳、TTL、sessionStorage、editLease API），前端与后端都变简单。
- 真正消除「静默丢失更新」：版本对不上就不能写，冲突可见。
- 顺带修 Web 全自动「基准图过旧覆盖 MCP」与「疑似自挡」两个隐患。
- Skill / 文档里的 `lockHeldBy` 叙事可删掉，造流路径更顺。

**缺点**

- 改动面大：库表、后端写图、MCP 重试、全自动重放、前端保存冲突分流、删锁、规程与文档都要动。
- 优先级反转：人有未保存内容草稿时，AI/MCP 仍可写；人点保存才可能撞冲突，需「放弃本地」或「强制覆盖」。
- 不做字段级合并；内容冲突只能整图二选一。
- 全自动冲突重放有失败可能（例如本轮要改的节点已被外部删除），需把原因回给模型/用户。
- 需迁移 SQL（`graph_revision`）与 guideVersion 变更后的 Skill 重 sync。

### 路线 B：保留写锁，仅坐标脏稿不占锁

- 新增 `isLayoutOnlyDirty(store)`：相对 `savedGraphSnapshot`，去掉 viewport 与各节点 `position` 后相同，且无 pending Staging。
- `useFlowEditLease`：layout-only 时不抢 / 释放长租约。
- `useExternalGraphSync`：layout-only 时收到外部写入，自动合入并写回本地坐标（否则保存会覆盖 MCP 写入）。

**优点**

- 改动小，基本只动前端；无需库表迁移，也不动 MCP / 全自动落盘。
- 直接解决本次触发点：一键排版、拖拽不再挡 MCP。
- 改了内容的草稿仍长占锁，人未保存时 AI/MCP 仍被挡，行为与现状接近，产品心智变化小。
- 风险低、可单独上线验证。

**缺点**

- §1.4 里其余锁问题仍在：机制重、关页残留、尽力而为、全自动基准过旧、疑似自挡。
- 改了节点/边/场景等内容的脏稿仍会挡住 MCP；录屏造流、边看边改场景依然会撞 `lockHeldBy`。
- 仍要做 layout-only 外部合入逻辑；若以后再走路线 A，这部分会重复一次。
- 租约相关代码与文档长期保留，技术债不减。

### 路线 C：能结合什么、不能结合什么

**硬冲突（无法同时要）**

A 的「AI/MCP 永远能写」与 B 的「人有内容草稿时挡住 AI」是同一把锁的两端，不能同时成立。必须先定产品优先级：人优先挡 AI，还是 AI 优先写、人保存时再解冲突。

**可叠加的部分**

| 能力 | 来自 | 说明 |
|:--|:--|:--|
| 仅坐标脏不占长锁 | B | 一键排版 / 拖拽不挡 MCP |
| layout-only 外部合入保留坐标 | A、B 都要 | 无锁时防保存覆盖；有版本时也省冲突弹窗 |
| `graph_revision` 条件更新 | A | 无论是否留长锁，都能消灭静默覆盖 |
| MCP / 全自动冲突重试或重放 | A | 版本冲突时的自动恢复 |
| 内容脏仍长占锁 | B | 保留「人草稿优先」心智 |

**两种可行折中**

**C1：版本校验 + 仅内容脏占锁（推荐折中）**

- 上路线 A 的 `graph_revision`、保存冲突分流、MCP 重试、全自动重放。
- **不删**长租约：仅当脏稿**不是** layout-only 时抢锁；排版 / 拖拽不占锁。
- layout-only 外部写入自动合入并保留坐标。

得到：排版不挡 MCP、无静默丢失、内容草稿仍挡 AI、全自动基准过旧可修。  
代价：改动面≈A，且**租约机制仍保留**（拿不到 A「删光锁」的简洁）；内容脏仍会撞 `lockHeldBy`。

**C2：先 B 后 A（分阶段）**

- 本周/本迭代只做 B，立刻消掉排版挡 MCP。
- `isLayoutOnlyDirty` 与外部合入可原样留给日后 A。
- 再开迭代做 A：加版本、删锁、改 Skill。

得到：B 的低风险与 A 的终态都有；中间一段时间仍背着锁债。  
代价：两期交付；B→A 时租约代码整段删除，有一次「装上再拆」的成本（合入逻辑可复用，不白做）。

**不建议的「假结合」**

- 只加版本、仍让任意 dirty 长占锁：排版挡 MCP 的问题原样还在。
- 只做 layout-only 跳锁、不加版本：无锁窗口里人手保存仍可能静默覆盖 MCP（B 必须靠外部合入补洞；合入失败或用户忽略条幅时仍有风险）。

## 3. 路线 A 改动范围

### 3.1 数据与后端

- `test_flow` 新增 `graph_revision BIGINT NOT NULL DEFAULT 0`；Domain / Result / Mapper / 建表与升级 SQL 同步。
  - 不用 `update_time` 当版本：同秒内两次写入可能无法区分。
- `updateTestFlow` 写图时：`UPDATE ... SET graph_json=?, graph_revision=graph_revision+1 WHERE test_flow_id=? AND graph_revision=?`；影响 0 行抛 `FlowGraphRevisionConflictException`（带当前 revision）。
- 查询流详情返回 `graphRevision`；`graphCommitted` SSE 事件携带新 revision。
- MCP 提交：冲突时重新加载图 → 重放本单元 → 重校验 → 重试，上限 3 次；仍失败返回明确错误（不再有 `lockHeldBy`）。
- Web 全自动：`TestFlowDesignRequest` 带 `baseGraphRevision`；落盘冲突时加载最新图，按 capture 已接受单元顺序重放，重校验后写；重放失败把原因回给模型与前端。
- 全局异常处理：版本冲突返回专用错误码与当前 revision。

### 3.2 前端

- store 记录 `graphRevision`；加载、保存成功、外部同步合入时更新。
- `saveFlow` 带 `baseGraphRevision`；收到冲突：
  - `isLayoutOnlyDirty` → 拉最新图，写回本地坐标，自动重存；
  - 否则弹窗：「放弃本地并拉取」/「强制覆盖」（二次确认，强制覆盖以最新 revision 重提）。
- `useExternalGraphSync`：layout-only 脏稿收到外部写入时自动合入并保留本地坐标（与路线 B 同一逻辑，两条路线都需要）。
- AI 设计请求带当前 `graphRevision`。

### 3.3 删除

- 后端：`FlowEditLeaseService`、`FlowEditLeaseConflictException`、`TestFlowController` 的 `editLease` 三个接口、`GlobalExceptionHandler` 对应处理、`McpToolInvokeService` / `CommitOutcome` 中的 `lockHeldBy` 与 `LEASE_CONFLICT_HINT`。
- 前端：`useFlowEditLease.ts`、`flowEditLeaseState.ts`、`acquire/heartbeat/releaseFlowEditLease` API、`X-Flow-Edit-Lease` 请求头、`FlowCanvasLayout.vue` 中的挂载与相关注释。
- `nodeChangeAffectsPersist` 的「误占写锁挡 MCP」注释改为只说标脏语义。

### 3.4 规程与文档

- [`CORE.md`](../qualitest-system/src/main/resources/cursor-skill/qualitest/CORE.md) 删「写锁仍被占用（lockHeldBy）」条目，改为「版本冲突服务端已自动重试；仍失败按错误提示重新勘察」；guideVersion 指纹随之变化，本地 Skill 需重新 sync。
- [`mcp.md`](./mcp.md) / `mcp.en.md` 第 137–139 行、`faq`、`ai-staging` 中的写锁描述同步改写。

### 3.5 测试

- 后端：版本条件更新成功 / 冲突；MCP 冲突自动重试成功与耗尽；全自动重放成功与目标节点已删时失败。
- 前端：`isLayoutOnlyDirty` 判定（仅移坐标 / 改 data / 增删节点）；保存冲突分流；外部同步 layout-only 合入保留坐标。
