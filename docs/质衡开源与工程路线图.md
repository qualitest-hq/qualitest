## 5. 已交付能力：被测数据快照与还原重试

> **不再单列开源阶段。** 节点级 checkpoint、`paused` / `resumeRun`、前端开关与决策 UI、demo `test-support-starter`、生产禁用护栏均已落地。原阶段 2（v1.1）任务清单已废止。

**能力摘要**：节点勾选 `snapshotBefore` → 执行前经 HTTP 调被测方 `/test-support/snapshot`；失败可暂停并由用户选择还原重试 / 原地重试 / 跳过 / 中止。质衡不直连被测库。环境 `allowDestructiveReset=0`（生产默认）时 checkpoint/restore 静默跳过；Starter 在 `prod` / `production` / `prd` profile 下不注册端点。

**使用约定**：**开启数据还原时，同一环境请串行跑**（还原会覆盖被测数据，平台暂不做环境级互斥锁）。

## 7. 阶段 4：v1.3 部署与数据迁移体系

**目标**：告别手工 upgrade SQL；质衡与靶场 **双仓各自 Compose**（一般人只起主仓）；需要时可用 `docker pull`（GHCR）。


| ID  | 任务                                    | 产出                                                                   | 估时   |
| --- | ------------------------------------- | -------------------------------------------------------------------- | ---- |
| 4.1 | **Flyway 接入**                         | `db/migration/V*.sql`；启动自动迁移；弃用手工 `upgrade_*.sql` 文档                 | 3～5d |
| 4.2 | **双仓独立 Compose（靶场）**              | ~~主仓 `--profile demo` 混栈~~ **废止**；demo 仓自有全栈 Compose（8081/8082；库 `qualitest-demo`）；主仓不混入、不为联调加 Flyway 迁移；demo **不接 Flyway**（dump + 场景 seed） | — |
| 4.3 | `scripts/dev-deps-up/down`            | 仅 MySQL + Redis，供本机 `mvn` + `yarn dev`                               | 1d   |
| 4.4 | GHCR 镜像发布                             | tag / 推送 `ghcr.io/qualitest-hq/qualitest`；README / deploy 附 pull 命令               | 1～2d |
| 4.5 | CI：`docker build` 校验                  | PR 只 build 不 push；与单元测试 Job 分离                                       | 1d   |
| 4.6 | `docker-compose.override.yml.example` | 本机改端口模板                                                              | 0.5d |
| 4.7 | （废止）GitHub Release                  | ~~`v1.3.0` Release~~ **不做**；Flyway 升级说明写入 `docs/deploy.md` | — |


**Flyway 要点**（运维约定见 [docs/deploy.md](./deploy.md)「库表迁移」；**仅质衡主仓**）：

- 将当前 `sql/qualitest_*.sql` 基线化为 `V1__baseline.sql`（或 baseline 标记 + 增量）。
- 历史增量依次编号为 `V2__…`、`V3__…`；**新功能只加 migration，不再改主 SQL dump 当升级路径**。
- 质衡用 Druid master 数据源，接入时须显式配置 `spring.flyway.url/user/password`。
- **`qualitest-demo` 不接 Flyway**：继续 initdb dump + 管理端 / `sql/seed` 场景加载。

**双仓独立 Compose 要点**（原「demo Profile」改判）：

- 主仓 Compose **永不**包含靶场服务；需要靶场时另 clone [`qualitest-demo`](https://github.com/qualitest-hq/qualitest-demo) 并按其 `docs/deploy.md` / `quick-start` 启动。
- 端口错开可并行：主仓默认 80/3306/6379；demo 默认 8081/8082/3307/6380。
- 联调环境 `baseUrl`：本机双进程用种子默认 `http://localhost:8081`；主仓 app 在 Compose 容器内时见 [`docs/deploy.md`](./deploy.md)（`host.docker.internal`）。

```bash
git init
git branch -M main
git add .
git commit -m "chore: initial open-source release"
git remote add origin https://github.com/qualitest-hq/qualitest.git
git push -u origin main
```

1. 公开仓库后启用 **Dependabot**、**Secret scanning** / **Push protection**（见 [§14.6](#146-dependabot-与-secret-scanning)；Settings → Code security）。

### 14.5 分支保护与 required checks

> **记一下，别回头忘了。**

| 条件 | 能否开 Protected branches / Require status checks |
| ---- | ------------------------------------------------ |
| 仓 **Public** + Org **Free** | ✅ 可用（公开日即可配） |
| 仓 **Private** + Org **Free**（当前 `qualitest-hq`） | ❌ 不可用；属 Team 起的「私有仓高级能力」 |
| 仓 Private + **GitHub Team**（或更高） | ✅ 可用（不必升 Team 仅为这一项；等公开更省） |

**约定**：

1. **Private 期**：CI 照跑；合 `main` 靠约定看绿，不强求 GitHub 强制拦截。  
2. **公开日动作**（三仓改 Public 后立刻做）：Settings → Branches（或 Rules）→ 保护 `main` → **Require status checks to pass before merging**，勾选 CI 里实际会出现的 check 名（如 `backend`、`frontend`；注意 path filter 下某侧可能 `skipped`，required 时 skipped 一般算通过）。  
3. 个人账号同理：私有仓需 **Pro**，公开仓 Free 即可。  
4. 官方对照：[GitHub’s plans](https://docs.github.com/en/get-started/learning-about-github/githubs-plans)（Team / Pro 的 private「Protected branches」）。

### 14.6 Dependabot 与 Secret scanning

> **一句话**：Dependabot = 依赖别带洞；Secret scanning = 别把钥匙推上网。公开日与分支保护一起开。

| 能力 | 做什么 | 入口 |
| ---- | ------ | ---- |
| **Dependabot** | 盯 `pom.xml` / `package.json` / `yarn.lock` 等依赖的已知漏洞与过期版本；出 **alert**，可开 PR 帮升版本 | 仓库 **Settings → Code security and analysis → Dependabot**（alerts + 可选 version / security updates） |
| **Secret scanning** | 按已知密钥模式扫仓库内容，发现疑似 API Key / Token / 口令等 | 同页 **Secret scanning** |
| **Push protection** | 推送时若像密钥则直接拦截（比事后扫更重要） | 同页开启 **Push protection**（建议与 Secret scanning 同开） |

**约定**：

1. **公开日**（三仓改 Public 后）：主仓优先开齐；demo / 插件仓同样建议开。  
2. Dependabot PR 不必见一条合一条：安全级优先审合；大版本升级可攒批次或标 `dependencies`。  
3. 扫到真密钥：立刻**轮换**该密钥，并确认已不在工作区 / 历史中（当前策略是从 0 公开，一般无旧历史，但仍要换掉已泄露的值）。  
4. 与阶段 0 本地脱敏互补：0.1 / 0.2 防「文件里写死」；本节能防「以后误推」与「依赖带洞」。  
5. 长期：§15.3 每季度过一遍 Dependabot；阶段 7 的「Dependabot 常态化」同此。

官方：[Dependabot](https://docs.github.com/en/code-security/dependabot) · [Secret scanning](https://docs.github.com/en/code-security/secret-scanning)
