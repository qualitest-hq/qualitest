# 测试编写约定（给人看的测试）

> 适用：`qualitest-system`（JUnit 5）与 `qualitest-ui/apps/web`（Vitest）。  
> 目标：失败时 30 秒内看懂「测什么、期望什么」；新生成的测试默认按本文，而不是「能跑就行」。

测试首先是**规格说明**，其次才是机器校验。机器绿了但人读不懂，等于给后人挖坑。

---

## 1. 三条总原则

1. **一个用例只讲一个故事**  
   名称负责扫读；**注释里的「前提 + 期望」**必须能单独回答场景（简单用例也不省）。
2. **断言对准行为，不对准实现细节**  
   优先验对外契约（返回值、状态、对外可见字段）；少绑私有结构、调用顺序、临时中间量。
3. **可读优先于花哨**  
   少魔法、少巨型 setup；公共夹具可以抽，但不要为抽而抽。

---

## 2. 命名：让列表里就能读懂

### 2.1 推荐形态

| 层 | Java（方法名） | Vitest（`it` / `test`） |
|----|----------------|-------------------------|
| 风格 | `动词或场景_关键条件或结果`（camelCase） | **中文短句**，或英文 `does X when Y` |
| 好例子 | `resolveNext_conditionIfBranch` | `demo-graph 往返不丢失 viewport 与 run` |
| 好例子 | `toAnthropicToolChoice_supportsNamedTool` | `无变更时回退文案` |
| 差例子 | `test1` / `testBuild` / `works` | `case1` / `ok` |
| 差例子 | `plainHttpUrl_appendsTestSupport`（像生成器标签） | 同上，堆砌英文缩写 |

前端已有好传统：`it('包含默认 viewport 与至少一条 run 场景')` —— **优先继续用中文短句**。  
后端方法名用英文标识符即可，但要用**可读的场景词**，不要用 AI 常见的 `whenX_thenY_givenZ` 超长串，也不要无无意义的 `shouldReturnTrue`。

### 2.2 类 / 文件名

- Java：`{被测类}Test`，与生产类同包或镜像包（现有 `com.qualitest.flow.*` 即可）。
- Vitest：`{模块或能力}.test.ts`，放在 `apps/web/src/test/...`，按领域分子目录（`flow/`、`project/`、`ai/`）。

### 2.3 分组与顺序

- Java：相关用例可 `@Nested` + `@DisplayName("中文场景")`（新增测试鼓励用；存量不强制改）。
- Java：**同一测试类内用例须显式排序**：类上 `@TestMethodOrder(MethodOrderer.OrderAnnotation.class)`，每个 `@Test` 加 `@Order(n)`（从 1 起，按「先基础后组合 / 先简单后复杂」编排）。便于本地跟跑与失败时对照列表顺序；不表示用例之间有状态依赖——用例仍应彼此独立。
- Vitest：用 `describe('被测单元或场景')` 分组，一组一事；文件内顺序即声明顺序，一般不必再标序号。

## 3. 结构：Arrange → Act → Assert

每个用例尽量三段，空一行隔开：

```text
// given / arrange — 准备输入与协作对象
// when  / act     — 只调用被测入口一次（偶发两次也要说清）
// then  / assert  — 少量、高信号断言
```

### 3.1 后端示例（推荐）

```java
/**
 * 前提：branch-graph 中 condition 节点，flow.code = 0。
 * 期望：命中 IF 分支，下一跳 n_ok，边为 e_if。
 */
@Test
@Order(1)
@DisplayName("condition 命中 IF 时，下一跳为 n_ok")
void resolveNext_conditionIfBranch() {
    GraphJson graph = loadGraph("flow/branch-graph.json");
    GraphWalker walker = new GraphWalker(graph);
    FlowRunContext ctx = new FlowRunContext();
    ctx.getFlow().put("code", 0);

    StepResult condResult = new ConditionNodeHandler()
            .execute(ctx, walker.getNode("n_cond"), "e1");
    String next = walker.resolveNextNodeId(walker.getNode("n_cond"), condResult);

    assertEquals("b_if", condResult.getBranchTaken().get("branchId"));
    assertEquals("n_ok", next);
    assertEquals("e_if", walker.findEdgeId("n_cond", next));
}
```

### 3.2 前端示例（推荐）

```ts
it('空环境 URL 时还原基址为空串', () => {
  // 前提：环境 URL 为空或仅空白
  // 期望：还原基址为空串
  expect(resolveResetBaseUrl('')).toBe('');
  expect(resolveResetBaseUrl('   ')).toBe('');
});
```

多个近似输入可以共用一个 `it`，但**标题要覆盖这组行为**；若期望不同，拆成多条。

## 4. 注释与文档：写「为什么」，少抄实现

新增测试**必须**有类/文件头与用例级「前提 + 期望」；简单场景也不例外。名称 / `@DisplayName` / 中文 `it` **不能替代**注释。

### 4.1 类 / 文件头（新增必选，固定三件套）

| 行 | 写什么 |
|----|--------|
| 测谁 | `测 {被测类或能力}：{一句话职责}` |
| 边界 | 纯函数 / 无 DB / 仅 fixture / mock 了谁 |
| 单跑 | 可复制的本地命令 |

**后端示例**

```java
/**
 * 测 ConditionBranchMergeHelper：patch 合并写入边时同步 condition 节点 branches[].target。
 * 边界：纯函数，无真实图执行。
 * 单跑：mvn test -DskipTests=false -pl qualitest-system -am -Dtest=ConditionBranchMergeHelperTest
 */
```

**前端示例**（文件顶块注释）

```ts
/**
 * 测 confirmFlowDesignUnit：mock 服务端 confirm API，含失败重试。
 * 边界：不启真实后端；Pinia 内存态。
 * 单跑：yarn test confirmUnit   （在 qualitest-ui 或 apps/web 下）
 */
```

单跑命令模板：

```text
后端：mvn test -DskipTests=false -pl qualitest-system -am -Dtest=XxxTest
前端：yarn test Xxx   （在 qualitest-ui 或 apps/web 下）
```

### 4.2 用例注释（每个 `@Test` / `it` 必选）

一律两行骨架（可再加一行补充），**简单场景也要写**：

```text
前提：{输入 / 状态 / 协作对象怎么摆}
期望：{对外可见结果是什么}
```

- 有 `@DisplayName` 或中文 `it` 时：注释仍写前提与期望；标题只负责列表扫读，不重复长篇复述。
- 不要在每个 `assertEquals` 上再贴一句同义废话。
- 夹具 / 魔数：为何是这个 id、代表哪个角色（开始节点 / IF 边等），写在用例注释或夹具旁。

**后端示例**

```java
/**
 * 前提：condition 出边新增，IF/ELSE 均尚未绑定 target。
 * 期望：首条未绑定分支（IF）写入 edge.target；ELSE 仍为 null。
 */
@Test
@Order(1)
@DisplayName("新增出边时绑定首个未绑定分支")
void syncConditionEdgeToNodes_bindsFirstUnboundBranch() { ... }
```

**前端示例**

```ts
it('普通 http 基址会自动补上 /test-support', () => {
  // 前提：基址为普通 http，无 path
  // 期望：末尾补上 /test-support
  expect(resolveResetBaseUrl('http://host:8081')).toBe('http://host:8081/test-support');
});
```

| 该写 | 不该写 |
|------|--------|
| 类头三件套；每用例前提 + 期望 | 把被测类源码复述一遍的长 JavaDoc |
| 夹具/魔数含义 | 每个断言上再贴同义废话 |
| 短而准（类头 3～8 行，用例 2～4 行） | 缺前提/期望，或注释膨胀成半页说明书 |

存量里 `GraphWalkerTest`、`ConditionBranchMergeHelperTest` 的方向是对的；新增时保持「短而准」，避免膨胀成半页说明书。

## 5. 断言：少而准

1. **先验结果，再验细节**  
   成功/失败 → 关键字段 →（可选）次要字段。
2. **一条用例 2～5 个断言为佳**；超过 8 个考虑拆用例或抽「期望对象」比较。
3. **避免**：
   - 只 `assertTrue(result.isSuccess())` 却不看关键数据；
   - 整段 JSON 字符串全等（一改字段全挂，且看不出差在哪）；
   - 依赖执行耗时 / 墙钟（除非专门测超时，且阈值要宽松或可配置）。
4. **消息**：失败时看不出原因的，用带说明的断言：

```java
assertEquals("n_ok", next, "code=0 应走 IF 分支");
```

```ts
expect(next, 'code=0 应走 IF 分支').toBe('n_ok');
```

## 6. 夹具与测试数据

- **小而具名**：`branch-graph.json`、`demo-graph.json` 这种比 `data1.json` 好。
- **能内联就内联**：三五行 JSON / 对象不必单独文件。
- **不要**把生产库导出、真实 Token、隐私数据放进测试资源。
- 前后端同一领域概念（节点 id、场景 id）尽量用**稳定的假 id**，并在注释里点明角色（开始节点 / IF 边等）。

Java 加载 classpath 资源；Vitest 用 `import x from './fixtures/....json'`。

---

## 7. Mock / 集成边界

| 类型 | 做法 |
|------|------|
| 纯单元（默认） | 只 mock 跨边界依赖（HTTP、DB、LLM 客户端）；被测类真实执行 |
| 协作对象 | 能用手写 stub / 假实现就别上复杂 Mockito 套路 |
| Mockito | **要么全用 matcher，要么全用实参**，不要混用（仓库里已有踩坑） |
| 前端 | 默认测纯函数 / store；组件 E2E 不放进日常 `yarn test` |

脚本引擎、图遍历等：**优先真实执行**；不要为了「单测纯度」把核心逻辑全部 mock 掉。

---

## 8. AI / 自动生成测试：生成后必审

生成器常见问题 → 合并前改掉：

| 现象 | 改法 |
|------|------|
| 方法名像标签：`plainHttpUrl_appendsTestSupport` | 改成场景句：中文 `it` 或 `resolveResetBaseUrl_plainHttpAppendsPath` |
| 类注释复述源码或缺三件套 | 压成「测谁 + 边界 + 单跑命令」 |
| 用例无「前提 + 期望」（含简单场景） | 每条补两行骨架；标题不能代替 |
| 一个方法里串 10 个无关场景 | 拆成多条 `it` / `@Test` |
| 断言魔法数字无说明 | 具名常量或注释「为何期望这个哈希」 |
| 为覆盖率测 private / 包内细节 | 改为测公共 API |
| 复制粘贴大段 setup | 抽 `fixture()` / `@BeforeEach` |

给 AI 的提示可直接贴：

> 按 `docs/测试编写约定.md` 写测试：一个用例一个故事；命名可读；AAA 结构；断言对准行为；类头三件套；每条用例写「前提 + 期望」（简单场景也要）；Java 用 `@TestMethodOrder` + `@Order`；不要为覆盖率测私有实现。

## 9. 后端 / 前端差异速查

| | Java (`qualitest-system`) | Vitest (`@qualitest/web`) |
|--|---------------------------|---------------------------|
| 框架 | JUnit 5 | Vitest |
| 可读展示名 | `@DisplayName` / `@Nested` | `describe` + 中文 `it` |
| 用例顺序 | `@TestMethodOrder` + `@Order` | 声明顺序即可 |
| 异步 | 少用；超时测要稳 | `async/await`；禁止 flaky sleep |
| 单跑 | `-Dtest=ClassName` 或 `ClassName#method` | `yarn test <文件名片段>` |
| CI | 全量 `mvn test` 修绿后纳入 CI | 已在 Actions：`yarn test` |

根 pom 默认 `skipTests=true`，本地要跑测试必须加 `-DskipTests=false`。

## 10. 评审清单（PR / 自检）

- [ ] 只看方法名 / `it` 标题，能否猜出场景？
- [ ] 类/文件头是否具备三件套（测谁、边界、单跑）？
- [ ] 每条用例是否有「前提 + 期望」（简单场景也不省）？
- [ ] Java 类是否 `@TestMethodOrder(OrderAnnotation)`，且每条 `@Test` 有 `@Order`？
- [ ] 失败时，断言消息或期望值能否指向业务原因？
- [ ] 是否只测一个行为？有没有顺手塞进无关断言？
- [ ] 夹具是否最小？有无真实密钥 / 脏数据？
- [ ] Mock 是否必要？matcher 是否用法正确？

---

## 11. 存量策略

- **不要求**一次性改写全部旧测试。
- **新文件、改动到的旧文件**：按本文收敛命名与结构。
- 发现「生成风」测试（难读、脆弱）：改行为时顺手整理，或单开小 PR 只做可读性。

## 12. 反例 → 正例（浓缩）

**反例（难读）**

```ts
it('plainHttpUrl_appendsTestSupport', () => {
  expect(resolveResetBaseUrl('http://host:8081')).toBe('http://host:8081/test-support');
});
```

**正例**

```ts
it('普通 http 基址会自动补上 /test-support', () => {
  // 前提：基址为普通 http，无 path
  // 期望：末尾补上 /test-support
  expect(resolveResetBaseUrl('http://host:8081')).toBe('http://host:8081/test-support');
});
```

**反例（缺前提/期望，注释抄实现）**

```java
@Test
void javascript_setFlowAndGetFlow() {
    // 这里用 ScriptRuntime 执行 JS，ctx.setFlow 会写入 flow map……
    FlowRunContext ctx = FlowRunContext.builder()
            .flow(new HashMap<>(Map.of("a", "hello")))
            .build();
    ScriptExecutionResult result = runtime.execute(
            ScriptConstants.LANGUAGE_JAVASCRIPT,
            "ctx.setFlow('x', ctx.getFlow('a'));",
            5000,
            ctx);
    assertTrue(result.isSuccess());
}
```

**正例**

```java
/**
 * 前提：flow 中已有 a=hello；脚本用 ctx 读写 flow。
 * 期望：执行成功，且 flow.x == hello。
 */
@Test
@Order(1)
@DisplayName("JS 可通过 ctx 读写 flow 变量")
void javascript_setFlowAndGetFlow() {
    FlowRunContext ctx = FlowRunContext.builder()
            .flow(new HashMap<>(Map.of("a", "hello")))
            .build();

    ScriptExecutionResult result = runtime.execute(
            ScriptConstants.LANGUAGE_JAVASCRIPT,
            "ctx.setFlow('x', ctx.getFlow('a'));",
            5000,
            ctx);

    assertTrue(result.isSuccess());
    assertEquals("hello", ctx.getFlow().get("x"));
}
```
